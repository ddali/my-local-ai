# 反馈怎么变成能力

## 偏差分类（对账用）

用户说不对、要加要减、做错了还是要完善，先想清自己原来的打算，再看差在哪一类：

| 偏差 | 表现 | 下次好使的做法 |
| --- | --- | --- |
| 方向 | 做出来的东西不是他要的 | 动手前把"你要的是 A 还是 B"确认掉 |
| 粒度 | 太粗或太细；他不要求的地方做过头 | 先给骨架等他点头，再定展开程度 |
| 顺序 | 该先确认却先动手，该先给方案却直接改 | 改结构、改规则类的事，先摆清单 |
| 范围 | 多做了不要的，或漏了他提过的 | 说清"这次不动什么" |
| 依据 | 借错方法、没核实就定方案 | 标清来源，前提不符就别套 |

只停在产出层改稿、不问当初为什么这么打算，同一处偏差还会再来。

## 根因维度（按需选用，不用逐条套）

| 能力维度 | 常见缺口 | 补强方向 |
| --- | --- | --- |
| 理解意图 | 把纠正当改稿需求、把追问读成新任务 | 先把反馈拆成"问题 + 标准"，确认后再动手 |
| 信息核实 | 凭印象猜、凭文件名猜、没核实就下结论 | 先核源头或实测，结论标待验证 |
| 判断取舍 | 用可执行性替代可判断性、只求跑通不问对不对 | 先问这是在加能力还是替用户做决定 |
| 表达输出 | 篇幅失控、套模板、黑盒无验证痕迹 | 先给结论和候选，讲前提与代价 |
| 自我校验 | 自己给自己记功、只验证可机械验证的部分 | 隔轮复核，验证对象对齐真实目的 |
| 协作节奏 | 该追问不问、该动手不动手、反复要人拍板 | 明确缺什么再问，能自己判断的直接做 |

## 一条条目回答的问题

写下来的判断，能回答这几件事才算站得住：这轮哪里不对；暴露的是哪个能力缺口；当时怎么想的、哪一步想错了；什么信号能在下次唤起警觉；什么表现说明又在犯。

模板（短，能删就删）：

```markdown
# <能力准则一句话>

- 维度：理解意图 / 信息核实 / 判断取舍 / 表达输出 / 自我校验 / 协作节奏
- 来源：<日期 + 哪次反馈或哪次翻车>
- 原计划：<原本打算怎么做，一行>
- 偏差：<差在哪，归到方向/粒度/顺序/范围/依据>
- 触发情境：<出现什么信号该召回>
- 准则：<以后怎么判断；跨任务可用，不绑工具和事务>
- 反例：<什么表现说明又在犯>
- 状态：已修正 / 待观察 / 再犯
```

没有反馈、只是顺利做完的任务，一行进能力索引就够，不展开条目。

## 回写去哪

- 判断结论进 `methods/` 或索引行，不只留在对话里。
- 同一缺口反复出现，并进 `methods/patterns.md` 成稳定准则；认可过的表达进 `style/`，反馈盲点进 `corrections/`，索引行标关联。
- 对用户有新的理解，补进 `shared/user-profile.md` 与 `shared/communication-guide.md`；新旧说法冲突以最新确认的为准。
- 同类问题再犯，在条目下补一句复发记录，必要时降级原方法。

## 能力边界

本地库能把纠错沉淀成判断修订和检查项，降低同类错误复发；改不了模型权重，也根除不了底层局限。确实超出能力的事，明说需要人工介入或换工具。
